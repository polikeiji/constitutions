# Application documentation

What an application's folder says about its stack, its shape as deployed, the pipelines that
ship it, and its tests. [tree-shape.md](tree-shape.md) names the sections and where they sit;
this file says what `tech-stack.md`, `architecture/` and `tests.md` contain.

## Rules

### The tech stack

1. `tech-stack.md` opens with the stack drawn as a `.drawio.svg` — see
   [diagrams.md](diagrams.md) rule 2 — then lists every piece the drawing shows: language,
   framework, runtime, data stores, hosting service, and any library a reader has to know
   about to change the code. Each piece carries one line on why it is there, since a stack
   listed without reasons is the one a later change swaps a piece out of without asking.
2. A version is the one the lockfile or manifest pins, and the list links that file rather
   than writing the number beside each piece. A version typed into prose is right the day it
   is typed and wrong the day the lockfile moves, and nothing fails when it does. A version
   no manifest pins — a managed runtime, a hosted database's engine — is stated, with a link
   to the infrastructure file that selects it.
3. A document for a narrower subject inside the application adds its own pieces to this
   list under the same two rules, rather than starting a second stack.

### The architecture

4. `architecture/` carries a drawn layout of the application as deployed — more than one
   drawing where a single one would pass the size in [diagrams-style.md](diagrams-style.md)
   rule 12. Between them, the drawings show:
   - **what the application talks to** — other applications, agents, batch processes,
     middleware such as databases, queues and caches, and external services — each
     connection labelled with its protocol and direction;
   - **who uses it** — every kind of user, human or machine, as its own element;
   - **how each kind of user is authenticated and authorized** — the identity provider and
     flow on the connection it applies to, and where the role or scope check is enforced;
   - **where it is deployed** — the environment and the hosting resource, each drawn as a
     container around what runs in it.
5. A user drawn without how they sign in tells a reviewer who reaches the application, not
   whether they should. So each kind of user's explanation beside the drawing — which
   [diagrams-style.md](diagrams-style.md) rule 21 requires of every element — names the
   credential it presents and the roles or scopes it can hold. The role names and scope
   strings live in code or configuration and are linked; a role list copied into prose is
   the first thing to drift when a role is added.
6. The estate the hosting resource sits in is `cloud/`'s drawing, linked rather than redrawn
   under [cross-referencing.md](cross-referencing.md) rule 4. An application's drawing shows
   the resource it runs on and stops there.

### The pipelines

7. The document explaining the architecture drawing ends with a **Pipelines** section naming
   every pipeline that builds, tests, deploys, or evaluates the application. Each gets one
   sentence on what it does and roughly when it runs, then a link to the workflow file and to
   its row in the `devops/` inventory. It sits under `architecture/` because pipelines are
   what put the application into the deployed state that section describes, and in one
   fixed place so that the next application's pipelines are where the last one's were.
8. A pipeline's jobs, permissions, secrets, and exact trigger are not restated there. The
   CI/CD constitution's [Documenting a workflow](../ci-cd/documenting-workflows.md) deletes
   a markdown copy of a workflow, and [cross-referencing.md](cross-referencing.md) rule 3
   allows a second document one sentence of orientation. Why a pipeline is built the way it
   is lives beside the workflow, where that document puts it.

### Tests and evidence

9. `tests.md` lists each automated suite: its kind — unit, integration, end-to-end — what it
   covers and what it leaves to another suite, what it needs in order to run, such as a
   database, an emulator, or credentials, and the command that runs it, linked where that
   command lives in a script or task file.
10. Results are links, never figures. Each suite links its latest run on the default branch,
    and coverage links the page the coverage tool produces. A pass count or a percentage
    typed into the document is true for one commit and reads as true for every commit after
    it. A coverage page committed to the repository is regenerated by a script there, and CI
    fails when the committed copy differs — the conditions
    [Documenting a workflow](../ci-cd/documenting-workflows.md) sets for the pipeline
    inventory, and for the same reason: a generated file nothing checks drifts like a
    hand-written one.
11. Evidence that one change was tested is its [UI test report](ui-test-reports.md) where
    the change is visible, and the pull request's checks where it is not. `tests.md` links
    the `test-reports/` index rather than listing reports: that index already lists every
    one, and a second list is the one that misses the next.
12. A suite that is skipped, quarantined, or not run in CI says so in `tests.md`, with the
    reason. A suite the document calls running and CI no longer runs is evidence nobody is
    collecting, presented as evidence somebody is.

## Rationale

Nearly every rule here ends in a link rather than a value. These documents are read by
someone about to change the application, and what that reader needs is where each truth
lives — the lockfile, the role definitions, the workflow, the latest run — because those are
what the change will touch. A value copied out of them is a second answer that only stays
right until the next commit, and the reader has no way to tell which commit that was.
